Recommendation

Make two changes separately. First, fix the three clone-unsafe stores while
preserving their current live-game meaning. Then implement zone-lifetime
identity for rule references. The second change addresses an actual opposite
failure. Riven Deserter's once-per-turn activation remained spent after Temporal
Breach returned the same backing Card as a new UnitInPlay in the same turn,
with three ready donors left to pay for it. A clone must keep the mark for the
same game object. A fresh game object should have its own mark under §124 and
Riven's printed restriction, read with §377.2.b.

2. WHEN IDENTITY CHANGES UNDER THE RULES
---------------------------------------

A physical card and the rules object it currently represents have different
lifetimes. Use the rules object for targeting and per-object usage. Keep a
separate way to correlate the underlying physical piece through zones.

| Event | Required treatment | CORE_RULES.md |
|---|---|---|
| Actual change of zone whose origin or destination is Non-Board | Fresh rules object. This includes deck to hand, hand to trash, trash to deck, play onto the Chain, permanent off the Chain onto the Board, and resolved spell off the Chain into trash. Clear old temporary modifications and statuses. The physical piece and its owner can still be tracked. | §§106–108, 124–124.2, 127.1, 354, 359.2, 359.3.d, 414.1, 417.1, 423.1, 428.1–2, 429.1–2 |
| Leave and return to the same zone or battlefield | Fresh object even if the same card returns immediately. An older target cannot reacquire it. The old source's once-per-turn use stays with that source incarnation. A per-player restriction still applies according to its wording. | §§124, 359.3.e.2–.4, 371.1, 377.2.b, 383.3.e, 386 |
| Move battlefield ⇄ base or battlefield ⇄ battlefield, including board-to-board control changes | Same object. Controller and location can make a target valid or invalid independently. If a unit moves to base and back before resolution, it can again meet a battlefield restriction. | §§107, 124, 190.3.a.2, 198.1–.2, 448.1–.3, 359.3.e.2–.3 |
| Rules action Recall, attach or detach, or a gear becoming a unit gear | Same object while it stays on the Board. Recall relocates to base. Returning a card to hand is a distinct operation. Equipment that detaches when its top-most card leaves remains in its own Board zone. | §§124, 143.5.b, 178, 457–460.1, 718.5–.6.a, 719.3–.5 |
| Hide a card, play it from facedown, reveal or reorder cards | Hand or Champion Zone to Facedown is a crossing into a Board sub-zone. Facedown to Chain is another crossing. Reveal alone is a state change, and reordering within the same deck does not change zone. | §§107.3, 108.1, 108.3, 124, 354, 422.1, 425.1.a–.2, 811.1.b–.c |
| Existing object becomes a copy or stops being a copy | Same object with changed copyable traits. Re-check predicates such as type or Might. Preserve that object's identity when the effect starts or ends, even if the engine changes the wrapper or Card used to represent its face. | §§124, 446.1–.2, 479.1.b–.c |
| Create a copy, or create an ordinary token | Fresh distinct object for every created piece. A Zilean-created copy or new Reflection has its own identity. Copyable characteristics come from the model, including earlier copy-layer traits where applicable. The source's damage, marks and history do not come with them. A Reflection already created keeps its own identity when it takes on traits. | §§180, 185–185.2, 440.1–.2, 446.3, 479.1.b.1–.c |
| Token moves to a Non-Board Zone other than the Chain | Process the applicable transition/departure, then the token ceases to exist immediately. Later token creation is independent. Death or leaves-board triggers may still need the departing token's information. | §§186–186.1, 383.2.c.3–.3.b, 429.1.a.1.b |
| Battlefield replaced by Brush, then swapped back | Explicit continuity exception. The replacement token occupies a fresh physical piece but is treated as the same battlefield game object for targeting and references, inheriting statuses and effects. The displaced card goes to Banishment as replaced. Swap-back ends the token and returns the card with current statuses/effects. | §§439.1–.1.a, 439.5–.7.b.1, 199.1 |
| A play is cancelled, a spell is controlled by another player on the Chain, or Repeat executes again | Undo a cancelled play, including its provisional identity change. Control or new choices on the same Chain Item preserve its identity. Repeat runs instructions again on the same item. A separate ability/cast on the Chain is a distinct item, even with the same physical source. | §§135.2.b.7, 191.5.b, 358.5, 402.1, 752–754, 820.1.d, 820.3.a |

Leaving play also has timing and reference exceptions. Preserve explicitly
saved pre-transition characteristics for a cost/effect's look-back. Capture
the departing source and needed characteristics when it triggers. An
already-created delayed ability can outlive its source. A linked effect can
refer to the new object in the destination zone when its text calls for it.
Bind that link to the particular event and destination object, e.g. "the card
I banished", so a later unrelated visit to that zone cannot satisfy the link.
Rules §§359.3.e.13–.14, 359.3.f.2–.3, 383.2.c.3, 391.5, 393, 398, 428.3.

Combat needs two concepts. A same-object move out of combat or a change of
controller can remove or switch designation. A unit already checked for its
Attack or Defend trigger does not re-check that same role in the same combat.
A new object arriving mid-combat is eligible for the appropriate designation
as an arrival. The current set serves both as a membership test and a history
of units processed by _open_combat. Preserve that behavior in the clone-only
patch. Test role history and current designation separately if correcting the
combat model. Rules §§323.2.a–.c, 383.4.e.2.a, 383.4.f.2.a, 466.2.c.3.a,
468.7.a–.c.

3. PROPOSED REPRESENTATION AND MIGRATION
---------------------------------------

A. Clone fidelity, with today's live-object lifetimes

Use graph references in the three stores as the small first fix. The relevant
Card and UnitInPlay classes have identity equality and hashing (eq=False).
A copied graph rehashes these keys and reconnects them to the copied card or
unit. Store the source Card in P1 with its existing discriminator, store the
marked UnitInPlay and turn in P2, and store the designated UnitInPlay in P3.
Migrate reads and writes together. This also avoids an address being reused
after its original object is destroyed. Keep these references bounded by
their existing turn/combat lifetimes. Retain current-turn marks for queued
old-source abilities until they have finished using them.

This is a deliberately small bridge. Card references preserve the current
behavior for a replayed backing Card, including the Riven case above. Keep
address-based copy memos and ephemeral combat modifier maps. Characterize
both pickle-based clone and deepcopy declaration before changing any zone
behavior. The clone boundary remains the GameState graph; a mid-task
continuation with its Python stack and pending loop work is a different
problem.

B. Rules lifetimes and value snapshots

1. Represent a rules object with a small immutable, game-scoped ObjectId
   allocated by a counter on GameState. Use a distinct type/tag so an object
   target cannot be confused with a mode number, action index, player or
   location. Preserve these values and the allocator on clone and deepcopy.
   Allocate on setup/admission, real creation, and a committed zone
   transition. Keep lookup pure. Use a game-local counter independent of the
   game RNG; never order actions/targets by ID. Treat IDs allocated on
   divergent sibling branches as branch-local. Preserve correspondence only
   for shared-prefix objects, or through the explicit deepcopy back-map.
   Two branches can legitimately allocate the same serial for different new
   objects.

2. Hold the current ObjectId on the canonical zone occupant/permanent, not
   its display name, copied Card face, or throwaway wrapper. A UnitInPlay and
   its backing physical piece agree on which in-play occurrence they
   represent. When gear gains or loses a UnitInPlay/DeployedGear wrapper, carry
   its Board ObjectId through. Preserve the underlying physical piece
   separately through transitions. Card.uuid already serves diagnostics and
   some search correlation. Keep that contract and resolve any face-swapping
   callers explicitly before equating it with a physical piece ID. The same
   Battlefield object is both a location and a rules object. Keep those
   references distinguishable and implement §439 continuity explicitly.

3. Freeze the ObjectId at the moment a target, grant, pending trigger, or
   linked effect is recorded. A reference to a mutable Card that is later
   consulted for its *current* ID recreates the same bug. Capture chain-item
   identity independently of its physical source and revalidate target
   predicates at resolution. For declared choices, lift the object parts
   into value snapshots while keeping the semantics of ordered choices,
   tuples, players and destinations. The Gear options in effects.py can
   include controller/holder metadata; do not use that metadata as the gear's
   identity. Snapshot the old source and required characteristics before
   moving it, and point a text-authorized link to the particular destination
   occurrence if needed. Apply this to the declared-board restoration and
   "it" paths where an old object is intentionally tracked. Keep temporary
   ranking/collection comparisons local. For the Irelia cost/target tie,
   capture the intended unit occurrence in the declaration snapshot.

4. Wire the boundary at actual operations rather than at list removal.
   The same list operation can implement moving, attaching, killing, or
   taking control. Start with admission and play, hand/trash/banishment
   transfers, and the hide path. Unit and gear play currently compress parts
   of rulebook Chain handling. Record the board occurrence at real entry
   and distinguish any actual ChainItem without changing finalization order
   to add identity. Route ordinary moves and recalls through the
   identity-preserving branch. Cover direct mutations in effects.py,
   notably _blink_unit, gear returns, conversions, and face copies. For
   _route_deaths, preserve batched handling and snapshot the departing
   occurrence after replacement is decided and before zone transfer.
   On an undone play restore the prior identity and state. Determinize is a
   new hidden-information hypothesis inside a search branch. Preserve known
   and public references when resampling and keep internal IDs out of
   player-visible observations.

5. Key source-bound uses by ObjectId plus the ability/instruction slot. Keep
   each existing player qualifier where the card text specifies a player,
   and keep player-only usage independent of any object's lifetime. Preserve
   the current slots in A. For B use a stable printed/granted slot, including
   the origin of each granted ability where appropriate. Do not collapse two
   different abilities just because their effect verb is identical. For
   Svellsongur, distinguish physical grant sources when moving beyond the
   current ordinal. A change of available abilities or list order must not
   rename the remaining use. Preserve already-used entries until the turn
   ends even when the originating object has left, for pending abilities
   carrying the old source ID. Maintain player scoping and once-consumption
   timing while making identity changes.

This ordering lets the three concrete clone failures land without a broad
zone-routing change. The zone model then fixes cross-zone targeting and
use/reset behavior under its own targeted tests.

4. TESTS TO WRITE, IN ORDER
--------------------------

1. Three red behavioral reproductions for A, using only public outcomes or
   the narrow relevant rule entry points.

   a. Black Market. Supply enough Power for two uses, activate once, then
      fork. In the original and both copied graphs, the active player gets
      the draw once and cannot immediately repeat. Verify the other player's
      separate use on their turn. Read the legal menu; don't only inspect a
      dictionary key.
   b. Combat. Open combat, copy before the showdown ends, then check that
      attacker/defender membership and a nonzero Assault/Shield bonus match.
      Re-enter _open_combat with the same units and verify no duplicate
      attack/defend triggers. Add a fresh arrival and verify that it alone
      gets newly designated. A clone can diverge afterward without changing
      the parent's board.
   c. Relentless Pursuit. Use its real spell to mark a runner and clone
      before conquer. Say yes to the triggered return in both worlds and
      observe the copied runner returning to base. Add a same-name unmarked
      unit and verify it isn't offered the grant.

2. Exercise both copy routes. Parameterize the three with GameState.clone
   (pickle path) and a deepcopy with the same agent exclusion used by
   declarations. Add one normal spell declaration that consults attacker/
   defender or current Might after copying. Check the before/after declaration
   trace and ensure the live source graph receives no speculative changes.
   Characterize a source-bound trigger/replacement, Riven versus her
   Svellsongur copy, and the per-player battlefield scope. Re-run all 28
   goldens here before starting B.

3. Write paired lifetime cases for B. With a pending target, move battlefield
   → base → same battlefield (target can still be valid) versus Temporal
   Breach (old target must be ignored, even with the same physical card and
   battlefield). Run a parallel base-gear case using a scripted leave/replay
   before the older target resolves, where the Python Card can be reused.
   For Riven Deserter, use the ability, move on the Board and check it stays
   spent, then banish/replay within the same turn and check the fresh object
   can use it. Test Mordekaiser's death replaced by heal/exhaust/Recall as
   the negative control. That is the same object and the replacement use
   remains spent. Verify independent targets on multi-target resolution too.

4. Add the exceptions and boundary cases. Cover Shady Spectacles copy and
   revert, a created Reflection or Zilean copy while the model is still in
   play, two distinct same-name pieces/tokens, token death or banish, and
   Brush replace/swap-back with an old battlefield reference on the Chain.
   Include attachment/detachment/type change, hand/Champion Zone → facedown
   → play, reveal alone, cancelled play, and Repeat versus a separate
   recast. Cover attached equipment staying on the Board when the host
   leaves. Assert that copyable traits, identity, and statuses each obey
   their own rule.

5. Cover references that outlive a mutation. Exercise Deathknell and
   pre-transition characteristics, pending once-limited triggers from an old
   source, banished-with links and a second unrelated trip to Banishment.
   Verify two branches can allocate and execute independently. Verify legal
   menus don't allocate IDs and deterministic playback preserves chooser
   ordering, RNG state, and observation privacy. Re-run clone, declared-target,
   combat, and legality tests with the full suite. Add at least one focused
   search replay where the compared branch actually exercises the identity
   fix, beyond the existing golden fixtures.

6. CONFIDENCE AND LIMITS
-------------------------

High confidence in the AST inventory and in the zone-lifetime distinctions
explicitly stated by the cited repository rules. I verified every one of the
96 sites is present in this appendix. I also checked that Card and UnitInPlay
reference keys reconnect correctly in both deepcopy and pickle on a small
object graph. That proves the reference-key bridge is mechanically feasible.

High confidence in the reproduced Black Market/combat defects from the prior
review and in the Relentless Pursuit and Riven Deserter reproductions added
here. The latter two probes use the real cards and current rule entry points.

Medium confidence in the detailed ObjectId migration. It is a proposed design;
its target snapshots, ability-slot provenance, explicit Replace exception and
zone-transfer wiring need the tests above before it can establish parity.
No engine or test source changes were made during this task. The proposed fix
has not been run against the fixtures. The zero-delta golden forecast is a
prediction supported by the observed baseline paths, with medium confidence
for the clone-only bridge and lower confidence for the zone-lifetime change.
PyTorch-dependent neural search behavior remains unverified in this runtime.
