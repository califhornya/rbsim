## Refactor sequence

1. **Freeze a decision-level baseline.** Keep the existing goldens and add differential traces from the pinned commit at decision and resolution boundaries. Compare the acting side, ordered legal actions and choice options, selected targets, charges, chain and trigger order, zone contents, RNG state, and terminal result. Normalize instance IDs consistently across runs while distinguishing two copies of the same card. Use both scripted answers, which expose the first divergence, and seeded agents, which expose downstream effects. Include declared targets that disappear before resolution, grouped moves, nested reactions, and abilities that keep priority. The main risk is a trace that omits the very state being changed, especially pending triggers or private information.

2. **Fix the proven defects in focused commits.** Replace persisted address keys with stable, copy-preserved identities. Define when a card or permanent gets a new identity and test copy, leave-and-return, and same-name cases. Introduce explicit execution outcomes for rejection, pass, successful action, and successful action that retains priority or focus. Use those outcomes in the live loop and search. Write targeted tests for both reproductions and review the resulting trace differences as deliberate behavior changes. Identity lifetime and the distinction between ending a grouped move and passing the turn are the highest-risk details.

3. **Share validation and execution one action family at a time.** Start with gear, where there is a concrete regression. Give menu enumeration and execution the same timing, destination, and cost checks. Keep payment, declarations, trigger flushing, and resolution in their existing order during extraction. Keep `GameAction`, existing tuple callers, and the current drivers as compatibility entry points. Test menu and execution agreement in all three windows and verify that rejected actions leave resources and board state intact. Add a strict test mode for unexpected handler failures so a failing effect cannot quietly count as a successful simulation in CI.

4. **Extract timing and effect boundaries after parity is established.** Give search and the live driver one transition interface. Make chain and showdown continuations explicit where search needs to fork them, including whose decision is pending, pass counts, and pending work. Narrow effect handlers’ access through operations the engine already owns, such as moving, paying, dealing damage, and queuing triggers. Migrate one caller and one effect family at a time. Run the default suite and decision traces on each extraction, plus the PyTorch suite before migrating neural search. Measure clone time and rollout throughput on fixed seeds because additional state copies can make a correct refactor impractical.

I’d leave a general-purpose card DSL, an event-sourcing rewrite, and performance tuning outside this refactor. Keep existing card handlers, policy defaults, and action ordering as the starting contract. **Confidence is high** that the first two phases address the reproduced failures. **Confidence is medium** in the exact continuation design until a migrated search caller passes parity and throughput checks.

## What stays unsolved

- **Official rules coverage.** Differential tests establish agreement with a baseline on exercised paths. They can preserve an existing ruling error and cannot establish correctness for untested card combinations. **High confidence** in that limitation. I did not independently verify the rules coverage.
- **AI fidelity and strength.** Correct cloning and transitions still leave hidden-information sampling and policy representation choices. For example, I verified that `action_to_index` encodes a unit at zero-based hand slot **11** and returns `None` at slot **12**. The engine menu and the neural policy therefore have different representational limits. **High confidence** in the encoding behavior. Frequency in actual games and impact on win rate are unmeasured.
